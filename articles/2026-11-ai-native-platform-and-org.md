**摘要。** 「AI Native」若只等于多买几个大模型或搭一套 Agent 运行时，企业会卡在「人人会用、利润表看不见」。公开调查与咨询研究反复指向同一缺口：工具扩散快，**工作方式与组织结构**跟上慢。本文从一条跨职能的业务闭环（标注为假设场景）出发，说明系统、流程、组织如何同时重构；再展开平台技术底座、责任与治理、演进路线、量化指标与反例。

## 1. 问题：AI Native 卡在哪一层

【研究事实】McKinsey 在 2026 年关于 AI 与组织的文章中引用其 State of AI 相关调查：多数受访者称个人生产力因 AI 改善，但报告正面 EBIT 影响的比例明显更低；高绩效群体中「实质重设计工作流」的比例远高于其他组织。[S4] 同系列 AI OS 文章还写到：在大公司样本里，扩规模使用 Agent 已不少见，但声称 AI 贡献至少 5% EBIT 的比例很低。[S7] 结论不是「模型不够强」，而是 **采用工具 ≠ 改写企业如何创造价值**。

【机构观点】Microsoft 2025 Work Trend Index 把目标态称为 Frontier Firm：系统由 AI 驱动运转、由人领导；混合「人 + Agent」团队；并给出助手 → 数字同事 → 人设方向、Agent 跑整段流程的三阶段图景。[S1] McKinsey 的 agentic organization 则用五支柱（商业模式、运营模式、治理、人才文化、技术数据）描述同一代际变化。[S3] 以上为机构提出的阶段模型与框架，**不是**跨行业统一的操作标准。

【作者综合】对企业一把手而言，AI Native 至少有两层，缺一不可：

| 层 | 回答的问题 | 常见误读 |
|---|---|---|
| **平台层** | 上下文、模型、Agent、工具、身份、策略、观测如何复用与可控？ | 以为「接上 API + 聊天框」就是平台 |
| **组织层** | 谁对端到端结果负责？决策权、激励、学徒制、例外升级如何改？ | 以为「全员开通账号」就是转型 |

只建平台、不改组织，会出现「系统建议很好、一线仍手工作业」；只喊组织变革、没有共享语义与治理面，会出现「每个部门一套互不复用的 Agent 栈」。下文先用一条业务闭环把两层钉在同一张图上。

保留必要的人工审核与例外处理，**并不等于**「不够 AI Native」——关键在于人机边界是否写清、责任是否可追溯，而不是自动化率本身。

## 2. 一条假设业务闭环：系统—流程—组织一起改

> **【作者综合 · 假设场景】** 以下「中型制造企业的订单履约异常闭环」为教学假设，用于说明建设顺序；**不是**某一家公司的脱敏案例，也不是作者团队的实测数据。

### 2.1 旧样态（职能接力）

客户下单后，异常（缺料、交期冲突、开票差异、客诉）在销售、计划、仓储、财务、客服之间工单流转。每人有自己的报表与 Excel；协调靠会议；「谁对客户承诺的交期负责」在组织图上模糊。

### 2.2 目标结果（端到端）

把「承诺交期可信、异常在时效内关闭、财务与库存账一致」定为唯一结果，而不是「客服响应更快」或「计划员报表更漂亮」这类局部指标。

### 2.3 系统怎么改

【机构观点 · 对照】McKinsey 所说的 AI OS（可理解为企业级智能操作系统：把语义、模型、Agent 与体验串成可治理的整体）把企业智能层描述为：语义层（实体、关系、政策、业务逻辑）+ 分析/确定性模型 + Agent 定义与编排 + 体验层；数据可先留在原系统，关系与定义在语义层生长。[S7] Google Cloud 的 Agent Platform 文档则把 Build / Scale / Govern / Optimize 收成统一控制面，并用 Registry、Identity、Gateway 管「谁能调什么」。[S8][S9]

落到本假设场景，最小系统能力可以是：

1. **共享业务对象**：订单、承诺交期、库存可用性、发票状态、客诉单——定义唯一，禁止同名不同义。  
2. **只读感知 Agent**：汇总会诊所需证据（BOM、在途、产能日历、未结应收）。  
3. **建议与起草 Agent**：给出改期/拆单/加急方案及对毛利、合约罚则的影响估计。  
4. **受控写入路径**：改承诺、锁库、开票调整必须走身份、策略与审批；未获授权的工具调用默认拒绝。  
5. **事件与回放**：每次建议、人工覆盖、最终动作可追溯（对应治理与学习，而不是事后甩锅）。

### 2.4 流程怎么改

【机构观点】McKinsey 强调以 AI 优先重设计工作流，而不是在旧流程上贴助手；高绩效与「实质重设计」相关。[S4] Microsoft 则强调到后期，人设定方向，Agent 运转流程，人在关键点介入。[S1]

假设闭环的新流程可以是：

1. 异常触发 → 系统自动组装证据包；  
2. 编排层提出若干可选动作及约束；  
3. 规则内动作由 Agent 执行，规则外升级到「结果负责人」；  
4. 关闭条件同时校验客户承诺、库存与财务状态，而不是只关客服工单。

### 2.5 组织怎么改

【机构观点】Microsoft 谈 Work Chart：按结果组队，而不是按职能永久切片。[S1] McKinsey 谈 orchestration chart（编排图）与 agentic team：少量跨职能人类监督端到端 Agent 编队；并提示协调类岗位过去膨胀，AI 应用来减少交接而非再加一层「AI 项目经理」。[S3][S4]

假设组织落点：

- 设立 **履约结果负责人**（对交期可信与异常关闭率负责），销售/计划/财务专家以嵌入方式参与，而不是各自只盯本部门考核。  
- 明确 **人保留的判断**：合约例外、重大客户关系、监管披露、超过阈值的商业让步。  
- 客服从「录单搬运」转向「解释取舍与安抚关系」；计划从「手工拼表」转向「挑战假设与处理边缘」。  
- 激励与晋升承认「编排 Agent 并交付结果」，而不是「亲手处理工单数量」。

没有这三步对齐，平台只会多几个聊天机器人。

## 3. 平台技术底座：共享上下文、编排与治理

### 3.1 平台要保护什么

【机构观点】McKinsey AI OS 给出一条总原则：**拥有上下文，租用或可替换模型与部件**。专有数据、制度知识、业务规则应可携带；锁死在单一供应商、难以迁出的「黑盒智能层」会削弱议价与演进能力。同时警告：每个职能各建一套互不互通的智能层，会毁掉企业级视图。[S7]

【作者综合】建设上应优先形成可跨域复用的共享控制能力；允许按监管或数据边界拆分子域，但应避免「每个试点一条不可复用烟囱」。

### 3.2 先闭环、后沉淀：可操作选型

【作者综合】平台不是第一天就要自建的。更稳妥的顺序是：

1. **先用现成托管能力或既有系统接口**，钉住一条跨职能闭环，验证结果链是否真的变短、变稳。  
2. **两个以上场景开始重复需要的能力**（例如统一业务对象、身份与策略网关、失败回放），再沉淀为平台组件；只服务一个试点的能力，不必急着「平台化」。  
3. **自建还是采购**，看三点：数据与合规边界（能否出域）、是否构成差异化壁垒、团队是否具备长期运维该层的能力。语义与核心业务规则通常应自控；通用模型、运行时、观测可采购或托管。  
4. **进入生产写入时**，至少覆盖：幂等（同一指令重复提交不致双写）、超时后的恢复与补偿、工具调用的权限继承与审计——缺一则不宜扩大自动写入范围。

### 3.3 能力分层（建设清单）

对照 McKinsey AI OS 分层与 Google Agent Platform 四柱，企业自建或采购时可按层验收：[S7][S8]

| 层 | 建设内容 | 验收问题 |
|---|---|---|
| 语义与知识 | 核心对象、政策、权限边界、术语表 | 换一个业务域，定义是否仍一致？ |
| 模型与分析 | 通用 LLM + 领域确定性模型（定价、风控、排程） | 高信任步骤是否仍靠可解释模型？ |
| Agent 与编排 | 可复用 Agent、工具契约、长任务运行时 | 新场景是拼装还是重写？ |
| 体验 | 嵌进现有 ERP/CRM/工单，而非另开孤岛 App | 一线是否在原工作入口完成？ |
| 治理面 | 身份、目录、策略网关、内容与语义策略、观测 | 未登记工具默认是否拒绝？ |
| 优化 | 评测、在线监控、失败回流 | 配置变更是否有回归集？ |

【研究事实 · 产品能力】Google Cloud 文档描述：Agent Identity 为每个 Agent 提供可审计身份；Registry 作为已批准 Agent/工具/MCP 的目录；Gateway 在入出站执行策略；默认连接拒绝，除非显式授权。[S9] 这是「平台级治理」的一种公开参考实现，不是唯一实现。

### 3.4 治理必须嵌入运行，而不是季度开会

【机构观点】McKinsey agentic organization 一文写：Agent 连续运行时，治理需实时、数据驱动、嵌在流程里；可用「批评 / 护栏 / 合规」类控制 Agent，但 **最终问责仍在人**。[S3] NIST AI RMF 1.0 则提供跨部门的自愿风险管理语言（映射、测度、管理风险），适合做董事会与管理层的共同词汇，而不是替代运行时网关。[S11]

【作者综合】把「模型安全评审会」当成唯一治理，挡不住运行中的越权调用；把「网关 + 身份 + 目录」当成唯一治理，又挡不住激励扭曲导致的人为覆盖。两边要扣在同一责任链上——下一节。

## 4. 组织责任体系：编排图、问责与激励

### 4.1 从组织图到编排图

【机构观点】McKinsey（2026-10）主张：先定结果，再组装人与 Agent；用编排图写清谁做什么、哪些交接消失、何处必须人判断。文中亦有产品研发团队在引入 Agent 后缩小编制的案例性描述，宜作示意，不宜当成编制公式。[S4]

【作者综合】编排图应能回答四句：这个结果的 **单一负责人** 是谁；Agent 可自主到哪条红线；超过红线升级给谁；覆盖 Agent 建议时如何记录理由。画不出这四句，就不该扩大生产写入权限。

### 4.2 问责：为什么「好员工」会关掉好系统

【机构观点】HBR（Narayandas, 2026）公开摘要指出：公司部署 AI 的速度快于治理重设计，系统容易停在「只建议、不进入真实决策」的位置；员工覆盖系统，常常因为 **不信任组织如何分担风险与责任**，而不是单纯不信任模型。[S5] 开篇银行信贷案例说明：风控与合规签字、试点指标好看，仍可能无法变成真实决策权。

【作者综合】责任设计要先于「提高自动化率」：

- 自动执行的动作 → 预置政策 + 审计 + 回滚/补偿；  
- 人机共决 → 人签字，系统保留推荐与反事实；  
- 禁止「出了事算算法、奖算部门」的双边套利。

### 4.3 人才、激励与学徒制

【机构观点】McKinsey 描述三类角色走向：跨域编排的督导、处理例外的深专家、把时间还给人际接触的一线。同时警告：若 Agent 吸走入门级练习活，今天的效率可能变成明天的判断力断层；激励与晋升需奖励编排与结果，而非仅奖励亲手吞吐。[S3][S4] HBR（Hoque / Davenport / Scade, 2026）提醒：许多「AI 裁员」叙事快于证据，更应重设计工作而非抢先砍编制。[S6]

【作者综合】激励最小集：

1. 结果指标与局部吞吐脱钩（或降权）；  
2. 对「合理覆盖 Agent」给制度空间，对「无记录覆盖」追责；  
3. 为新人设计新的练习场（模拟单、影子模式、专家复盘），替代被自动化掉的学徒活。

## 5. 演进路线：三阶段与可复用交付单元

### 5.1 三阶段（机构地图）

【机构观点】Microsoft：助手（个人提效）→ 人机团队（Agent 接任务）→ 人领导、Agent 运转流程。[S1] McKinsey：在灯塔域大胆重设计，同时铺扩展使能条件；并用「agentic mission factory」（可理解为可复用的端到端交付单元：一次把使命、人机工作流、控制与可复用资产做齐）避免试点无限增生。[S4] 上述阶段划分是机构地图，各企业落地节奏会不同。

【作者综合】阶段可以并存，但 **生产写入权限与激励规则** 必须按业务域控制开放节奏，避免全公司同时处于「无人负责的第三阶段想象」。

### 5.2 建议节奏（作者举例，非普遍承诺）

下表时长为作者便于讨论的举例，**不是**对所有企业的承诺周期。

| 阶段（举例） | 焦点 | 退出条件（示例） |
|---|---|---|
| 前期 | 选 1 条跨职能结果链；只读感知 + 语义最小集；画编排图与红线 | 异常关闭周期有基线；结果负责人已点名；只读链路通过预设验收用例 |
| 中期 | 受控写入；身份/目录/策略网关；激励试点；失败回流 | 写入路径通过幂等与超时恢复测试；审批与审计链路可回放；回退演练通过 |
| 后期 | 第二域复用语义与 Agent；压缩互不复用的烟囱；管理节律改为时效干预 | 第二域接入成本明显低于第一域；业务结果与体验指标可解释 |

平台工程（运行时、评测、发布控制等）在此作为 **使能投资**，服务跨域复用，而不是单独讲成「研发工具现代化」。

## 6. 量化指标与反例

### 6.1 建议同时看的四类指标

【作者综合】单一「采用率」会骗人。建议并列：

1. **业务结果**：端到端周期、一次解决率、承诺兑现率、差错/泄漏、单位成功成本；  
2. **工作重构**：跨职能交接次数、会议用于对齐信息的时长、编排图覆盖的流程比例；  
3. **治理健康**：越权拦截数、无记录覆盖率、策略变更审计完整率、严重事件平均处置时间；  
4. **组织信任与能力**：员工是否相信组织会公正处理 AI 带来的岗位变化（McKinsey 将组织信任与价值实现相关联）；[S4] 新人达到独立判断所需时间。

【研究事实】Microsoft WTI 给出的领导者比例、McKinsey 给出的个人生产力 vs EBIT 落差，应用作「行业背景」，不要直接写成你公司的考核目标。[S1][S7]

### 6.2 反例（看见就停）

| 反例 | 症状 | 为何危险 |
|---|---|---|
| 只开通、不见结果 | 全员有账号，利润表上看不出贡献 | 停留在个人助手层 |
| 烟囱 Agent | 每部门私有栈与私有术语 | 无法编排跨域结果 |
| 建议停在纸面 | 模型永远只建议，无人改决策权 | 与 HBR 所述「停在顾问位」同类风险 [S5] |
| 先裁后设计 | 以 AI 叙事裁员，流程未重画 | 伤害信任与学徒制 |
| 治理外置 | 只有季度委员会，无运行时强制 | 规模化后越权与失控风险显著上升 |
| 指标单腿 | 只盯用量或采用率 | 优化了成本，丢了结果 |

## 7. 结语与建设检查清单

AI Native 企业不是「更会写代码的公司」，而是 **能把专有上下文变成可编排行动，并能改写责任与激励的公司**。平台提供共享上下文、编排与治理；组织提供编排图、问责与人才系统；两者在同一条业务结果链上会合。

**建设前自检（每一项都应能指向平台或组织）：**

- [ ] 是否选定了一条跨职能业务结果，而不是一个部门工具？  
- [ ] 语义与对象定义是否有主人？  
- [ ] Agent/工具是否进目录，未批准调用默认拒绝？  
- [ ] 编排图是否写清人机边界与升级路径？  
- [ ] 激励是否奖励结果与编排，而非局部吞吐？  
- [ ] 是否有信任与学徒制安排，避免「好员工系统性覆盖」？  
- [ ] 第二域能否复用第一域资产？  
- [ ] 指标是否同时覆盖结果、重构、治理、信任？  
- [ ] 生产写入是否具备幂等、超时恢复/补偿与权限继承？
